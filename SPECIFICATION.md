# SPECIFICATION.md — MicroCrop

**Продукт:** MicroCrop — Micro-SaaS веб-сервис онлайн-кроппинга и кадрирования видео на стороне клиента.
**Тип документа:** Product & Technical Specification
**Версия:** 1.0
**Дата:** 2026-09-18
**Автор:** Senior Solution Architect / Product Owner (draft)

## 1. Executive Summary & Goals

### 1.1 Суть продукта

MicroCrop — веб-сервис, позволяющий пользователю быстро обрезать (Trim/Cut) и кадрировать (Crop) видеофайл прямо в браузере, **без загрузки исходного видео на сервер**. Вся обработка видео происходит на клиенте с помощью **FFmpeg.wasm** (WebAssembly-порт FFmpeg), что даёт:

- **Privacy-friendly** обработку — видео пользователя никогда не покидает его устройство;
- **Нулевую нагрузку на сервер** в части видеопроцессинга — сервер не хранит и не транскодирует медиафайлы;
- **Мгновенный отклик** — нет необходимости ждать загрузку/выгрузку файла по сети.

### 1.2 Бизнес-цель

Дать SMM-специалистам, контент-мейкерам и обычным пользователям простой one-shot инструмент для:
- превращения горизонтального видео в вертикальное (под Reels/Shorts/TikTok/VK Клипы);
- быстрой нарезки нужного отрезка ролика;
- кадрирования кадра под нужный формат/соцсеть.

Ключевое отличие от конкурентов (Kapwing, Clideo и т.д.) — **обработка на клиенте**, что снижает серверные издержки практически до нуля и позволяет держать сервис бесплатным в базовом функционале при минимальных операционных расходах.

### 1.3 SEO-цель

Основной канал привлечения пользователей — органический поиск. Сервис должен иметь набор посадочных страниц (landing pages), заточенных под частотные запросы, например:

- «обрезать видео онлайн»
- «кадрировать видео онлайн бесплатно»
- «обрезать видео для Reels/Shorts»
- «сделать вертикальное видео из горизонтального»
- «сделать круглое видео для Telegram»
- «нарезать видео на части онлайн»
- «обрезать видео 9:16 / 1:1 / 16:9 онлайн»

Каждая такая страница — отдельный URL с уникальным Title/Description/H1, но использующий общий UI-компонент редактора (предзаполненные настройки пресета, например открытие сразу с рамкой 9:16).

### 1.4 Монетизация

1. **Реклама (РСЯ — Рекламная сеть Яндекса)** — показ баннеров пользователям бесплатного тарифа (шапка, боковая панель, экран ожидания рендера).
2. **Разовый микро-платёж через Robokassa** (эквайринг для самозанятых, режим НПД) — за:
   - снятие водяного знака "microcrop";
   - ускоренную обработку (приоритетные оптимизации/пресеты);
   - доступ к пресетам под конкретные соцсети (готовые размеры/битрейты).

Модель без обязательной подписки: пользователь платит один раз за один экспорт/сессию (PRO-токен), либо покупает подписку на период (опционально, v2).

### 1.5 Ключевые метрики успеха (KPI)

- Конверсия из органического трафика в использование редактора (не требует регистрации);
- Конверсия «бесплатный экспорт → покупка PRO-токена»;
- CTR/RPM рекламных блоков РСЯ;
- Позиции в поиске по целевым SEO-запросам;
- Время до первого экспорта (Time-to-Value) — цель: < 2 минут с момента открытия страницы.

## 2. User Personas & Use Cases

### 2.1 Персоны

| Персона | Описание | Потребность |
|---|---|---|
| **SMM-менеджер / контент-мейкер** | Ведёт соцсети, ежедневно готовит короткие вертикальные ролики | Быстро перегнать горизонтальное видео в 9:16 под Reels/Shorts/TikTok/VK Клипы, без водяного знака (готов платить) |
| **Обычный пользователь** | Разово хочет обрезать кусок видео (например, для отправки друзьям или в Telegram) | Максимально простой интерфейс, бесплатно, без регистрации |
| **Микро-бизнес / фрилансер** | Готовит короткие рекламные/промо-ролики | Нужны готовые пресеты под конкретные платформы, скорость |

### 2.2 Ключевые Use Cases

**UC-1. Кадрирование горизонтального видео в вертикальный формат**
Пользователь загружает 16:9 видео → выбирает пресет 9:16 (Reels/Shorts/TikTok/VK Клипы) → перемещает область кадрирования по кадру (может двигаться по X во времени, MVP — статичная область на весь ролик) → рендерит → скачивает MP4.

**UC-2. Нарезка временного интервала (Trim/Cut)**
Пользователь загружает видео → на таймлайне выставляет маркеры начала и конца → получает обрезанный по времени фрагмент без изменения кадра.

**UC-3. Комбинированный сценарий (Crop + Trim)**
Пользователь одновременно выбирает временной интервал и область кадрирования → один рендер-проход → получает готовый ролик под соцсеть.

**UC-4. Снятие водяного знака (конвертация в PRO)**
Пользователь на экране предпросмотра/после первого рендера видит водяной знак → нажимает «Убрать водяной знак» → оплачивает через Robokassa → получает токен → повторный (или тот же) рендер уже без вотемарки.

## 3. Functional Requirements

### 3.1 Frontend

#### 3.1.1 Загрузка видео
- Drag-and-Drop зоны загрузки на главной и посадочных страницах;
- Альтернативный выбор через `<input type="file">`;
- Поддерживаемые форматы на вход: MP4, MOV, WebM, AVI (в пределах того, что декодирует ffmpeg.wasm/браузер);
- Ограничение размера файла на клиенте (например, до 300–500 МБ — с учётом ограничений памяти WASM в браузере), с явным предупреждением пользователю при превышении.

#### 3.1.2 Плеер предпросмотра и Crop Box
- Видеоплеер с оверлеем — прямоугольная рамка выделения области кадрирования (**Crop Box**);
- Контролы фиксированных соотношений сторон: **16:9, 9:16, 1:1, Free** (произвольное соотношение, ресайз мышью/тач за угловые маркеры);
- Перетаскивание (drag) рамки по кадру;
- Числовой ввод/отображение координат и размеров области (для точной настройки);
- Live-обновление превью при изменении рамки.

#### 3.1.3 Таймлайн (Trim/Cut)
- Горизонтальный таймлайн с миниатюрами кадров (thumbnails, опционально в MVP);
- Два маркера-хендла — точка начала и точка конца обрезки;
- Отображение текущего выбранного диапазона в формате `чч:мм:сс.мс`;
- Возможность точного ввода времени начала/конца вручную;
- Проигрывание только выбранного диапазона в предпросмотре.

#### 3.1.4 Рендеринг (клиентский, FFmpeg.wasm)
- Вся операция кадрирования/нарезки выполняется в браузере через `ffmpeg.wasm` (fluent-ffmpeg-подобный пайплайн: `-vf crop=...`, `-ss`/`-to` для триминга);
- Индикатор прогресса рендера (% выполнения, если доступно из ffmpeg.wasm логов);
- Экран ожидания/рендеринга — отдельный UI-стейт с местом для рекламного блока (см. 3.1.6);
- Обработка ошибок рендера (недостаточно памяти, неподдерживаемый кодек и т.п.) с понятным сообщением пользователю.

#### 3.1.5 Watermark (водяной знак)
- На бесплатном тарифе итоговое видео получает наложение полупрозрачной надписи **"microcrop"** в правом нижнем углу (реализуется через `drawtext`/`overlay` фильтр ffmpeg на этапе клиентского рендера);
- Водяной знак накладывается **только** если у пользователя нет активного PRO-токена на данную сессию/экспорт;
- Water-mark не накладывается повторно, если пользователь уже купил снятие ограничения (см. 3.2).

#### 3.1.6 Скачивание результата
- Кнопка «Скачать» — сохраняет готовый файл в форматe MP4 (через Blob/URL.createObjectURL, без пересылки на сервер);
- Понятное имя файла (например, `microcrop_<timestamp>.mp4`).

#### 3.1.7 Рекламные блоки (РСЯ)
Контейнеры для рекламных блоков РСЯ размещаются:
- в шапке (header banner);
- в боковой панели (sidebar, на десктопной раскладке);
- на экране ожидания/рендеринга (пока идёт клиентская обработка видео — «занимаем» внимание пользователя, у которого объективно есть время ожидания).

Блоки должны быть адаптивны (скрываться/менять размер на мобильной раскладке), не должны показываться PRO-пользователям на этапе, где реклама расположена рядом с оплаченным функционалом (по решению продукта — MVP: реклама показывается всем, кроме экрана без вотемарки после оплаты, если это будет мешать UX).

### 3.2 Backend & Payments

Backend в данном сервисе **не участвует в обработке видео** — его роль ограничена: SEO-страницами (SSR/шаблонизация), платежами и выдачей токенов доступа к PRO-функциям.

#### 3.2.1 Генерация ссылки на оплату Robokassa
- Backend-эндпоинт формирует ссылку на оплату Robokassa (разовый платёж — покупка PRO-токена на снятие водяного знака / ускоренную обработку / доступ к соцсеть-пресетам);
- Подпись запроса формируется по правилам Robokassa (MD5-подпись параметров с использованием `MerchantLogin`, `OutSum`, `InvId`, паролей #1/#2);
- Продавец зарегистрирован как самозанятый (режим **НПД** — налог на профессиональный доход), чек формируется через интеграцию Robokassa с приложением «Мой налог» (автоматическая передача данных о доходе в ФНС при оплате).

#### 3.2.2 Webhook / Callback (ResultURL) от Robokassa
- Backend принимает `ResultURL` callback от Robokassa после успешной оплаты;
- **Валидация подписи** входящего запроса (MD5 или SHA256 хэш по формуле `OutSum:InvId:Пароль#2`, сравнение с параметром `SignatureValue`);
- При успешной валидации — фиксация оплаты в БД (таблица `payments`/`orders`), привязка к сессии/пользователю, кому выдать доступ;
- Ответ Robokassa в формате `OK<InvId>` при успешной обработке (согласно протоколу Robokassa).

#### 3.2.3 Выдача токена доступа (снятие ограничений)
- После подтверждённой оплаты backend выдаёт клиенту короткоживущий **JWT/API-токен** (например, TTL 24–48 часов), подтверждающий право на:
  - экспорт без водяного знака;
  - ускоренные настройки рендера (если применимо — на клиенте это может означать другие параметры кодирования, например меньший битрейт/более быстрый preset x264, раз обработка всё равно локальная);
  - доступ к premium-пресетам под конкретные соцсети.
- Токен хранится на клиенте (localStorage/cookie) и передаётся при повторных рендерах в рамках его срока действия;
- Backend должен предусматривать эндпоинт валидации токена (для случаев, когда фронтенду нужно перепроверить актуальность токена, например при обновлении страницы).

### 3.3 Данные и модели (высокоуровнево)

Минимальный набор таблиц в БД:
- `orders` — заказы/платежи (Robokassa `InvId`, `OutSum`, статус, дата, привязанный токен/сессия);
- `pro_tokens` — выданные PRO-токены (значение, `expires_at`, `order_id`, статус использования);
- (опционально v2) `users` — если вводится регистрация/личный кабинет истории покупок.

## 4. Non-Functional Requirements & Environments

### 4.1 SEO-оптимизация

- **Мета-теги**: уникальные `<title>`, `<meta name="description">`, Open Graph теги (`og:title`, `og:description`, `og:image`, `og:type`) для каждой посадочной страницы и общих страниц сервиса;
- **Семантическая верстка**: корректная иерархия заголовков (`h1`–`h3`), использование `<main>`, `<article>`, `<nav>` и т.д.;
- **`sitemap.xml`** — генерируется на стороне Laravel (динамически, на основе списка посадочных страниц/пресетов), доступен по `/sitemap.xml`;
- **`robots.txt`** — генерируется/раздаётся Laravel-роутом, с указанием ссылки на sitemap и правил индексации (открыт для основных ботов, закрыты служебные маршруты вида `/api/*`, `/admin/*`);
- **Рендеринг для индексации**: контент посадочных страниц (текст, заголовки, FAQ) должен быть доступен в исходном HTML-ответе — используется **Blade-шаблонизация** Laravel (SSR по умолчанию для Laravel-приложения) для страниц-обёрток; сам интерактивный редактор (Crop/Trim UI на FFmpeg.wasm) подключается как SPA-виджет/JS-компонент внутри Blade-страницы, не блокируя индексацию текстового контента страницы;
- Структурированные данные (JSON-LD, тип `WebApplication`/`SoftwareApplication` и `FAQPage` для блоков FAQ на посадочных страницах) — рекомендуется для расширенных сниппетов в поиске.

### 4.2 Технологический стек и окружение

- **Backend**: PHP / Laravel (Blade-шаблонизация страниц, роуты для sitemap/robots, обработка платежей Robokassa);
- **Frontend/редактор**: JS/TS SPA-компонент, интегрированный в Blade-страницы; клиентский видеопроцессинг — **FFmpeg.wasm**.

### 4.3 Локальное окружение базы данных

|---|---|

### 4.4 Совместимость с Node.js

- Основная целевая версия для сборки фронтенд-ассетов (Vite/Webpack, ffmpeg.wasm-зависимости): **Node.js 18**;
- При недоступности Node 18 в окружении — допускается fallback на **Node 16** при условии указания необходимых флагов совместимости (например, `--openssl-legacy-provider` для сборщиков, использующих устаревшие вызовы OpenSSL-провайдера в Webpack 4/5 под новыми версиями OpenSSL);
- Версия Node фиксируется в `package.json` (`engines`) и/или `.nvmrc` для консистентности окружений разработки и CI.

### 4.5 Производительность и ограничения клиентской обработки

- Обработка видео полностью на клиенте означает зависимость производительности от устройства пользователя (CPU/память браузера); необходимо:
  - предупреждать пользователя о примерном времени рендера для больших файлов;
  - ограничивать максимальный размер/длительность входного файла для предотвращения зависания вкладки;
  - использовать Web Worker (штатный режим ffmpeg.wasm) для рендера, чтобы не блокировать UI-поток.

### 4.6 Безопасность

- Валидация подписи Robokassa callback — обязательна (защита от поддельных уведомлений об оплате);
- PRO-токены — короткоживущие, подписанные (JWT), проверка подписи на backend при необходимости серверной валидации;
- Никакие видеофайлы пользователя не передаются и не сохраняются на backend — вся обработка и все данные видео остаются в браузере пользователя.

### 4.7 Совместимость браузеров

- Поддержка последних версий Chrome, Firefox, Edge, Safari с поддержкой WebAssembly и SharedArrayBuffer (требуется для многопоточного режима ffmpeg.wasm; необходимо выставлять корректные заголовки `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` на сервере для активации `SharedArrayBuffer`);
- Fallback-сообщение для браузеров без необходимой поддержки WASM/потоков.
